## 3. Архитектурные правила

- UI — в компонентах; бизнес-логика и расчёты — в `utils`; повторно используемое состояние/сценарии — в `hooks`.
- Один файл — не более 700 строк. Большой модуль сначала разделить по ответственности, не переносить монолит в другой файл.
- Не дублировать существующие функции, компоненты, типы и справочники: сначала искать аналоги.
- Новые зависимости добавлять только при доказанной необходимости; предпочитать бесплатные решения.
- Не использовать платные или обязательные внешние API.
- Не использовать `Math.random()` для пользовательских прогнозов.
- Не менять формулы расчётов ради прохождения теста. Сначала установить причину и сохранить/добавить эталонные проверки.
- Не заявлять о безопасности, шифровании, точности или offline-поддержке, если это не реализовано.
- Внешние сервисы и передаваемые им данные должны быть явно отражены в документации и UI.
- После каждого существенного изменения запускать релевантные тесты; перед завершением — `npm run verify`.

## 4. Git и разрешение конфликтов

- Работать только в активной feature/fix/chore-ветке; для нового независимого этапа создавать новую ветку от актуальной базы, если пользователь не указал продолжить текущую.
- Никогда не коммитить напрямую в `main`, не менять её и не выполнять merge без разрешения пользователя.
- При конфликте версий одного файла выбирать **только более новую версию файла**. Старую версию не оставлять; содержимое двух версий не объединять.
- Перед разрешением конфликта определить, какая версия новее, по истории/коммитам. Если однозначно определить нельзя — остановиться и запросить уточнение, не угадывать.
- После разрешения конфликта проверить импорты, ссылки, типы и тесты, которые могли зависеть от удалённой старой версии.
- Не переписывать историю и не force-push без явного разрешения.
- Не открывать PR и не сливать ветку без отдельного запроса.

## 5. Definition of Done

Задача завершена только если:
- изменён минимально необходимый набор файлов;
- нет дублирующей или устаревшей реализации;
- добавлены/обновлены тесты для изменённого поведения;
- `npm run verify` завершился успешно либо конкретная внешняя блокировка описана;
- документация обновлена, если изменились поведение, ограничения или архитектура;
- изменения находятся в разрешённой ветке, `main` не затронута;
- итоговый статус и оставшиеся риски указаны явно.
