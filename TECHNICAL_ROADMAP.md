# TECHNICAL_ROADMAP

## 1. Текущее состояние

- Проект: AstroDay, React 18 + TypeScript + Vite; расчёты выполняются преимущественно в браузере.
- Активная ветка: `feat/astroday-production-audit`.
- База ветки: `main`; последняя проверка: ветка опережает `main`, отставание 0. Счётчик коммитов меняется при каждом обновлении.
- `main` не изменять. PR не открывать без отдельного запроса.
- Этап: production-аудит, стабилизация CI, расширение Васту и добавление анализа жизненных сфер/партнёрской карты. Релизная готовность не подтверждена.
- Раздел Васту: выбор цели (достаток/отношения/самочувствие), компасная сетка 3×3, рекомендации по 9 секторам, сохраняемый чек-лист, денежная карта дома, выбор направления-фокуса по финансовой задаче, 4 типа remedies и блок применения принципов к аренде/продаже/управлению недвижимостью.
- CI: workflow `.github/workflows/ci.yml` добавлен. Последний run для `feda6e3`: строгий TypeScript check прошёл; тесты хранения, девяти направлений и Васту прошли; полный verify остановился на известной ошибке звёздного времени в `astrology.test.ts`. Production build в этом запуске не достигнут.
- Натальная карта: добавлена вкладка анализа денег, карьеры, развития, благополучия и отношений по соответствующим домам и планетам. Добавлена форма карты супруга/партнёра, поиск места рождения через Nominatim, сохранение профиля локально и вывод межкартных аспектов без числового «рейтинга совместимости».
- `verify` теперь выполняет строгую проверку TypeScript перед unit-тестами, чтобы ошибки типов не скрывались за падением теста Асцендента.
- Текущий блокер CI: `astrology.ts` вызывает `Astronomy.SiderealTime`, но в Node ESM это значение не является функцией. Падает `astrology.test.ts` при расчёте Асцендента. Исправление `MakeTime` в `ayanamsha.ts` прошло соответствующие regression fixtures.
- `npm run verify`: unit-тесты → строгий TypeScript → production build. Полный успешный прогон пока не подтверждён.
- `npm ci` сообщил о 10 уязвимостях зависимостей: 2 low, 1 moderate, 5 high, 2 critical. Состав и фактический риск ещё не разобраны.
- В `storage.ts` функция `saveUserProfile` перехватывает ошибку записи и не сообщает вызывающему коду о неудаче. Риск ложного подтверждения сохранения.
- Ветка содержит исправление privacy notice: профиль и расчёты локальны; Nominatim получает поисковую строку или координаты при геокодировании.
- Чек-лист Васту хранится отдельно в localStorage и удаляется вместе с данными дома. XOR-обфускация localStorage обратима и не является шифрованием. Полноценной серверной части нет.
- Редактор плана квартиры теперь создаёт пустой рабочий холст, поэтому комнаты можно размечать до загрузки изображения. Для точного анализа загруженный план всё ещё должен быть ориентирован севером вверх.

## 3. Архитектурные правила

- UI — в компонентах; бизнес-логика и расчёты — в `utils`; повторно используемое состояние/сценарии — в `hooks`.
- Один файл — не более 700 строк. Большой модуль сначала разделить по ответственности, не переносить монолит в другой файл.
- Не дублировать существующие функции, компоненты, типы и справочники: сначала искать аналоги.
- Новые зависимости добавлять только при доказанной необходимости; предпочитать бесплатные решения.
- Не использовать платные или обязательные внешние API.
- Не использовать `Math.random()` для пользовательских прогнозов.
- Не менять формулы расчётов ради прохождения теста. Сначала установить причину и сохранить/добавить эталонные проверки.
- Не заявлять о безопасности, шифровании, точности или offline-поддержке, если это не реализовано.
- Внешние сервисы и передаваемые им данные должны быть явно отражены в документации и UI.
- После каждого существенного изменения запускать релевантные тесты; перед завершением — `npm run verify`.

## 4. Git и разрешение конфликтов

- Работать только в активной feature/fix/chore-ветке; для нового независимого этапа создавать новую ветку от актуальной базы, если пользователь не указал продолжить текущую.
- Никогда не коммитить напрямую в `main`, не менять её и не выполнять merge без разрешения пользователя.
- При конфликте версий одного файла выбирать **только более новую версию файла**. Старую версию не оставлять; содержимое двух версий не объединять.
- Перед разрешением конфликта определить, какая версия новее, по истории/коммитам. Если однозначно определить нельзя — остановиться и запросить уточнение, не угадывать.
- После разрешения конфликта проверить импорты, ссылки, типы и тесты, которые могли зависеть от удалённой старой версии.
- Не переписывать историю и не force-push без явного разрешения.
- Не открывать PR и не сливать ветку без отдельного запроса.

## 5. Definition of Done

Задача завершена только если:
- изменён минимально необходимый набор файлов;
- нет дублирующей или устаревшей реализации;
- добавлены/обновлены тесты для изменённого поведения;
- `npm run verify` завершился успешно либо конкретная внешняя блокировка описана;
- документация обновлена, если изменились поведение, ограничения или архитектура;
- изменения находятся в разрешённой ветке, `main` не затронута;
- итоговый статус и оставшиеся риски указаны явно.
